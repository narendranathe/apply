# Orchestrator failure artifacts

The actual production run `40050463437` failed without a downloadable artifact. The workflow already uploads `run-output/summary.json` and encrypted backups with `if: always()`, but the orchestrator's exception entry point only prints its safe diagnostic and exits. The earlier maintenance-script correction does not cover `python -m cloud.orchestrator`.

Factor argument construction into `_argument_parser()` and move the existing operational body unchanged into `_run(args)`. Keep `main()` as the existing parse-and-run interface: its callers still receive the original exception. The module entry point calls a small `_cli()` wrapper that parses once, invokes `_run`, and handles an operational exception. This avoids either scanning `sys.argv` separately for `--output` or changing the raising contract of `main()`.

On failure, compute `_failure_summary(error)` once. Persist exactly that already-sanitized dictionary to the parsed output destination, print the same dictionary, and preserve exit status 1. Both the default `run-output/summary.json` and an explicit output such as `run-output/research-fallback-summary.json` must work. Argument-parser exits retain their existing behavior. The successful operational body, output and exit behavior remain unchanged.

The failure writer performs local filesystem work only. Traverse output directories using directory descriptors and `O_DIRECTORY | O_NOFOLLOW`; create missing directories with mode 0700. Require the final output parent to belong to the current user, then restrict it to 0700. Open the final filename with `O_NOFOLLOW`, require an owned regular file with one hard link before truncating, and restrict it to 0600. A symlink, special file, hard-linked target, unavailable directory or other filesystem error leaves the original safe stdout diagnostic and nonzero exit intact. Absolute output paths must use canonical, non-symlink directory components; the hosted Linux paths and relative workflow outputs meet this condition.

There is no backup, recovery attempt, storage retry, transport call, Notion read/write or provider request after an exception. No exception text, response body, header, credential, contact data or message content is added to the summary. Existing diagnostic classification and operational guards remain unchanged.

Validation exercises the actual module entry point with an injected pre-operation failure, rather than merely testing the writer in isolation. Tests cover default/custom destinations, direct and wrapped Notion errors with private sentinels, original exit status, zero later backup/transport activity, restrictive permissions, filesystem failure, final/ancestor symlinks and hard-linked targets. Separate tests retain `main()`'s exception identity and successful CLI output behavior. Passing local tests do not establish hosted artifact retention; root owns deployment and actual hosted validation.
