# Recovery of the October 22 evidence-only storage incident

The owner has authorized completion of the migration without routine interactive confirmations. This design implements that existing authorization; it grants no new provider, application or messaging permission.

The failed maintenance run `39718240610` on `28b550aba1bf8b7d5be93494e3e146f68e675fe3` left exactly the first protective profile quarantine. Authenticated snapshot `39780427733` contains 2,898 pages and 2,651 CORE records, preserving all previous 2,897 pages, 2,650 CORE records, 757 historical records, the whole ready record and every effect signature. Two auxiliary unverified observations are absent. Their writes remain uncertain and must never be repeated. No writer-resolution POST was reached: two full 2,897-page scans at the pinned serial 0.4-second request interval require at least 2,317.2 seconds before that code path, while the actual hosted operation lasted 1,398 seconds.

Three approaches were considered. Repeating the old six-record operation would violate its explicit partial-batch safeguard. Waiting for an unavailable upstream request receipt would retain safe research-only operation but cannot currently settle the missing observations. The selected approach is a single incident-specific immutable correction epoch: preserve the operational hold, reserve the two uncertain IDs permanently, preserve their full original CORE evidence in one new audit bundle, and append only the three provably unattempted writer resolutions. This is limited to these auxiliary observations, never business intents, receipts or outbound effects.

## Evidence and architecture

`cloud/contained_recovery.py` owns one fixed V3 protocol. It authenticates the original three source captures and constructor/delta proof, failed maintenance source/run/job/diagnostic/timing proof, the actual one-hold snapshot and its committed encrypted archive, baseline and unchanged ready record. IDs, source hashes, timestamps, archive/member hashes and expected CORE hashes are compiled reviewed constants; callers and environment inputs cannot supply replacements.

The existing `cloud/readback_reconciliation.py` and its proper-partial-batch rejection stay unchanged. V3 is a separate `reconcile-contained` maintenance mode under the existing common concurrency group, owner/main checks and `CLOUD_ENABLED=false`. The repository must remain on the execution head while it runs. It never invokes business lanes, imports history, changes the ready record or changes feature variables.

`cloud/storage_reservations.py` contains the two fixed reserved top-level record IDs and expected evidence hashes. `NotionStore.put` rejects either ID before preflight, queries or creation. Reservation checks apply to the actual top-level record identity; the new bundle can legitimately embed those IDs as evidence. There is no expiry, opt-out or alternative-ID creation mechanism for the uncertain observations. Reads remain available.

The bundle is one new `audit_events` record containing the exact two original CORE records, the authenticated encrypted packet and attestation references, one-hold source proof, timing proof and explicit permanent `storage_unknown`/no-create/no-retry/no-alias dispositions. It states that the original cohort did not complete and does not pretend the embedded observations existed as standalone pages. It lists the three resolution IDs without hashes to avoid a hash cycle. All three V3 resolutions use the same evidence, including the bundle and hold whole-CORE hashes and the original strict business proof. They retain global external reconciliation false, native delivery false, native history incomplete, index incomplete and no retry authorization. The original lead resolution is last.

## Write boundary and startup verification

Before writing, the entire fresh source must exactly match the authenticated one-hold state. Both reserved old IDs must still be absent. After appending the new bundle, take another full source snapshot, remove only that exact bundle and require the same source fingerprint. Recheck main, current maintenance context and original/maintenance evidence before the three resolutions. Post-write readback must be exact; only absent reads may be polled with no creation retry. A proper subset of the new four appends is another incident and stops. An exact complete repeat is read-only.

The new cohort binds its actual owner/main/attempt-one execution run and source head through independently verified native GitHub context. Before any new append, complete maintenance-run history must prove there is no prior invocation that could have entered this correction writer. An empty observed cohort after a previous failed invocation is still uncertain and cannot be recreated. A complete exact four-record cohort may be reverified and backed up without writes; startup clearance additionally requires a successful same-head, same-protocol hosted verification with complete job and artifact evidence, so a failed final backup cannot unlock production.

The new state is five required records: the original hold, new bundle and three V3 resolutions. It adds exactly four pages/CORE records to the captured one-hold state: 2,902 pages and 2,655 CORE records. Independent authenticated backup verification must establish those exact additions and preserve every prior page/CORE and effect signature.

Every production wake selects the strict V3 matcher only for its exact schema and known original failure IDs. The matcher freshly reads all five required records and both reserved IDs, requires same-evidence complete peer resolutions, and rechecks all three original failed attempts/jobs plus the failed maintenance attempt/jobs and source-capture run/jobs. Reruns, incomplete pagination, edited or duplicate records, read errors and any later appearance of either reserved old ID fence production. Even an exact late arrival requires a new independent reconciliation; it never clears the hold or permits a retry. Unknown schemas cannot fall through to generic startup/manual clearance.

## Durable verification receipt

GitHub artifacts expire after fourteen days. Before startup can accept V3, an independently authenticated recovery proof and the actual encrypted complete backup must be committed at the fixed `recovery-evidence/2026-10-22-contained-verification.json` and `recovery-evidence/2026-10-22-contained-complete.aesgcm` paths. They are outside the five protocol-source files, so publishing verified evidence does not change the execution source binding. The runtime validates this trusted repository receipt, ciphertext hash, exact five-record cohort hashes, actual execution binding and successful verification run, then freshly checks native run/jobs/source witnesses. It does not rely on expired artifact availability. Absence of a receipt fences production even when every cohort row exists. The independently authenticated partial-source ciphertext is also retained in private Git.

## Completion gates

Required evidence before production enablement: independent constructor/pin review, meaningful negative regressions, complete local and hosted CI, actual central V3 success and authenticated full backup. Then perform a guarded production run, complete persistent index/backup verification, a same-Chicago-day no-effect rerun and a real hosted research-agent admission/consumer test. Research-only remains enabled throughout. Any production failure rolls `CLOUD_ENABLED` back to false and preserves research. There are still no authorized live LinkedIn or employer-specific application submission integrations; those remain explicit capability exceptions.

The design has no unresolved routine implementation decision. It preserves the old gate, the permanent operational suppression, all historical evidence and all uncertain writes; the selected correction changes their evidence custody without replaying them.
