# Bounded candidate progress

The application lane currently limits the score-sorted feed before checking history. Five previously blocked roles can occupy every later run while unmatched supported roles remain in the tail. Discovery repeats its fixed AI/data selection without reading its existing job observations. The five-role budget is intentional; the lack of progress within that budget is the defect.

Use a stable partition with the existing identity matcher. Applications retain qualified/prepared work without an attempt first, then unmatched roles, then other retryable covered roles. Applied, unknown, submitting, terminal or attempted matches are counted as duplicates before the verification budget. Existing in-loop dedup, canonical employer/requisition checks, official verification, truthful qualification, preparation, permission, receipt and pacing gates remain unchanged. Selection never clears an employer-level hold or creates another identity. An explicit `employer_history_unresolved` flag always holds the application; a missing-requisition match also holds unless it shares an already-known canonical URL. Exact-URL parser placeholders with no attempt remain retryable. The same suppression predicate runs before budgeting and at both pre- and post-official identity checks; ambiguous holds are counted with one static reconciliation exception label.

All matching application identities are checked using the existing canonical matcher on the already-loaded rows. A prepared row cannot hide an applied, unknown, attempted or ambiguous peer because of dictionary order. Immediately before the external request, the existing fresh application query must contain exactly one matching whole CORE equal to the expected submission-eligible claim; every additional matching identity or changed CORE stops with `application_claim_changed`. No extra Notion query or automatic identity merge is introduced.

Explicitly typed application events and reported submission claims in the feed are independent suppression evidence even when prepared or verified work already matches. Preserve each exact stable claim as its own revision-zero `submission_unknown` application observation, with reported status/date retained and no inferred receipt. Feed-claim identity and payload exclude export timestamps and age, so unchanged claims do not append on every wake. Typed events retain their existing source-event-derived identity, full event hash and unresolved-history semantics; ordinary outreach prose is never interpreted as an application. Existing prepared and receipt-bearing records remain immutable. New observations require full CORE readback; uncertain writes/readbacks stop without retry. Idempotence compares the original immutable claim by raw record ID from the same initial query, while eligibility retains the latest folded transition. A later verified/closed outcome therefore does not masquerade as original-source corruption, and an actually changed original CORE still stops.

Discovery treats an application match or an existing job observation match as covered. Apply the existing AI/data allocation to unmatched roles first, then fill remaining capacity from covered roles while retaining the original overall AI target when available. Existing applied/unknown roles can still receive research when capacity remains; discovery cannot authorize applications or outreach.

A durable application or job observation advances the next run to unseen roles without adding cursors, record kinds, services or configuration. Unchanged covered roles remain available for later rechecks after unmatched work is exhausted. Failures with no durable observation can be retried under the same existing safeguards; this change does not infer that a failed operation completed.

Rejected alternatives: increasing the limit increases runtime without solving starvation; random/date rotation adds nondeterminism and can defer prepared work; a new cursor/planner introduces migration and reconciliation state beyond this fix.

Validation uses synthetic official GET responses and durable in-memory record stores. Reproduce the same five identities on two old-code runs, then prove later runs advance through unseen identities under the existing five-role limit. Cover in-flight priority, unknown/applied/attempt and URL-alias suppression, distinct requisitions, employer-level uncertainty, discovery-only coverage, mix allocation, empty feeds and fallback to covered work. No real provider request or operational write is used.
